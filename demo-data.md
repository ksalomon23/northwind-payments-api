# Demo data: seeded dependency findings

Generated by running `npm install` then `npm audit --json` against this repo's
actual `package-lock.json` on 2026-11-22. These are **real, currently-published**
advisories for the exact versions pinned below - not invented IDs.

**CISA KEV check:** none of the four findings below are listed on the CISA
Known Exploited Vulnerabilities catalogue. KEV is reserved for vulnerabilities
with confirmed active exploitation, almost always in network/enterprise
infrastructure products (VPNs, firewalls, OS kernels), not application-level
npm library ReDoS/prototype-pollution bugs. Don't claim KEV status for these in
the demo - say "high severity per the GitHub Advisory Database / npm audit,"
not "actively exploited" or "on the KEV list."

## Finding 1 - lodash (clean patch bump, no code change)
- **Package:** `lodash` (direct dependency)
- **Installed:** 4.17.20 -> **Fixed in:** 4.17.21
- **Advisories:**
  - GHSA-35jh-r3h4-6jhm - Command Injection in lodash
  - GHSA-29mw-wpgm-hmr9 - Regular Expression Denial of Service (ReDoS)
- **Fix type:** patch version bump only (`4.17.20` -> `4.17.21`). No call sites change.

## Finding 2 - axios (minor bump, no code change)
- **Package:** `axios` (direct dependency)
- **Installed:** 0.21.1 -> **Fixed in:** 0.21.4 (or later 0.x/1.x line)
- **Advisories:**
  - GHSA-wf5p-g6vw-rhxx - Cross-Site Request Forgery
  - GHSA-cph5-m8f7-6c5x - Inefficient Regular Expression Complexity (ReDoS)
- **Fix type:** minor bump within the 0.x line. No call sites in this repo use
  the affected config surface, so no code change is required - good contrast
  against Finding 3, which does need one.

## Finding 3 - jsonwebtoken (breaking change, needs a code edit)
- **Package:** `jsonwebtoken` (direct dependency, used in `src/auth.ts`)
- **Installed:** 8.5.1 -> **Fixed in:** 9.0.2
- **Advisory:** GHSA-qwph-4952-7xr6 - signature validation bypass due to
  insecure default algorithm handling in `jwt.verify()` (algorithm confusion).
- **Fix type:** **breaking.** v9 requires an explicit `algorithms` allowlist
  on every `jwt.verify()` call; without it, verify throws. This repo's
  `src/auth.ts` currently calls `jwt.verify(token, JWT_SECRET)` with no
  algorithms option - the fix PR must add `{ algorithms: ["HS256"] }` (and
  the matching change in `src/__tests__/payments.test.ts` if signing options
  change), which is the "small breaking change" the build brief asks for.

## Finding 4 - express + path-to-regexp (direct + transitive, minor bump)
- **Package:** `express` (direct) pulling an old `path-to-regexp` (transitive)
- **Installed:** express 4.17.1 -> **Fixed in:** express 4.21.2 (brings a
  patched `path-to-regexp` transitively)
- **Advisories:**
  - GHSA-rv95-896h-c2vc - Express.js open redirect in malformed URLs
  - GHSA-9wv6-86v2-598j / GHSA-rhx6-c78j-4q9w - `path-to-regexp` ReDoS
- **Fix type:** minor bump, no code change expected (verify in CI).
